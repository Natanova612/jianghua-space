# PRD：「问姜华」—— 站点交互核心（草案 v0.1）

> 状态：讨论稿，未动工
> 日期：2026-08-12
> 背景：站点从「陈列式门面」升级为「交互式产品」。JD 匹配器已验证可行性（5 份真实 JD 测试，评分梯度 90/68/52/48/10，判断质量达标），现将其扩展为站点的主体模块。

---

## 一、产品定位

**一句话**：站点即产品，产品即证明——访客通过与「姜华的 AI 分身」对话，完成岗位匹配、合作评估、了解其人其作。

**双层站点架构**：
- **核心层（交互）**：「问姜华」对话 —— 站点的心脏
- **栏目层（陈列）**：案例志 /work、思考集 /notes、其人 /about、简历 /resume —— 高级杂志式编排

**两个定位的承载**：
- Plan A（客户/合伙人）：合作可能性分析 + 案例 + 文章
- Plan B（面试官）：岗位匹配 + 简历 + 案例证据链

## 二、用户与场景

| 角色 | 进来干什么 | 核心路径 | 目标动作 |
|------|-----------|---------|---------|
| 面试官/HR | 验证这人是否匹配岗位 | 首页 → 选「我是面试官」→ 粘 JD → 结构化报告 → 追问细节 | 发邮件约面 |
| 潜在客户（文旅企业主等） | 这人能不能帮到我 | 首页 → 选「我有合作」→ 描述业务 → 获得合作形式建议 | 发邮件/加即刻 |
| 潜在合伙人 | 看看是不是同路人 | 首页 → 随便聊聊 → 了解经历与思考 | 深聊 |
| 普通访客 | 被画卷吸引逛进来 | 浏览 → 好奇发问 → 留下印象 | 关注/传播 |

## 三、首页结构（卷首改造）

三层背景保留（画/字/人）。「人」层的核心从静态文字变为对话入口：

```
卷首
├─ 姜华 + 名章（保留）
├─ 三行定位（保留）
└─ 【对话区】（新增，替代一切 CTA）
    ├─ 引导语：「山水已阅，不如开口。」（拟）
    ├─ 输入框（单行，回车发送）
    ├─ 三个意图签：我是面试官 ｜ 我有合作或项目 ｜ 随便聊聊
    └─ 对话展开区（首条发送后原位展开，流式逐字呈现）
```

设计原则：
- 对话区是卷首的「第四行字」，初始状态轻（一行输入框），对话发生后才展开——不破坏画卷的安静
- 回答中涉及作品/简历时，AI 主动给链接（站内导流回栏目层）
- 移动端：对话区全宽，键盘弹出体验优先

## 四、对话核心功能规格

### 4.1 三意图
- **我是面试官**：引导粘 JD → 结构化输出（匹配度/匹配点附证据/差距风险/建议）→ 可多轮追问（"他 SQL 到底什么水平？"）
- **我有合作或项目**：先问诊（业务、卡点、目标）→ 给合作可能性判断（能帮什么、不适合什么、建议形式）→ 不适合的直说并给替代建议
- **随便聊聊**：开放问答，边界内知无不言

### 4.2 技术规格
- 接口：`POST /api/chat`，流式（Moonshot SSE → 纯文本增量直出）
- 模型：kimi-k2.6（temperature 固定 1，平台限制）
- 记忆：会话级（前端保留最近 16 条，刷新清空；不做持久账号体系）
- 限流：10 次/分钟/IP；单次输入 ≤4000 字
- 降级：接口挂 → 显示「分身暂时离线，邮件可直接找到本人」+ 邮箱

### 4.3 护栏（安全红线）
1. 话题边界：只谈职业相关；政治/隐私/无关请求礼貌引回
2. 事实边界：profile.json 是唯一事实源，禁止编造经历数据
3. 注入防护：拒绝"忽略指令/扮演他人"类请求
4. 隐私红线：家庭、收入、健康等不答，引导邮件问本人
5. 人设边界：明确自己是"AI 分身"，第三人称谈姜华，不冒充本人

## 五、内容安排

### 5.1 能力底稿（profile.json）扩容
现状：技能/经历/gaps。需补：
- `faq_knowledge`：高频问题的标准答案（收费吗？怎么合作？base 哪里？时间投入？）
- `cases_digest`：每个案例的 3-5 句精华 + 链接（供对话引用导流）
- `voice`：语气样本（几段姜华自己的文字，让分身说话更像"他的人"）

### 5.2 栏目层（杂志化，后续阶段）
- /work 案例志：自有作品全开放 + 职场案例脱敏复盘（自绘示意图）
- /notes 思考集：文旅平话范式（content-playbook.md 已定）
- 栏目页被对话引用 → 形成「对话激发阅读，阅读激发对话」的循环

## 六、运营细节（需要对齐）

1. **对话日志**：要不要存访客问了什么？
   - 价值：知道市场关心什么（面试类多还是合作类多）、发现分身答错的地方
   - 代价：涉及访客输入的存储，需在界面注明「对话内容可能用于改进服务」
   - 建议：存（仅问题文本+意图类型，脱 IP），Vercel KV 或简单日志
2. **成本控制**：k2.6 按 token 计费；当前限流 10 次/分/IP 兜底；建议 Vercel 侧设用量告警
3. **灰度**：先仅自己测试一周 → 再挂首页？还是直接上？（建议：功能直接上首页但保持 BETA 标，真实反馈即是打磨）
4. **与 /resume 匹配器的关系**：建议匹配器保留（它是结构化工具），但其按钮改为引导到对话版？或两者并存观察使用偏好
5. **英文访客**：分身自动随访客语言切换，无需额外设计

## 七、风险

| 风险 | 缓解 |
|------|------|
| 模型延迟 40-60s 体验差 | 流式输出（首字 ~5s 内可见）；后续关注更快的模型 |
| 分身说错话/被注入 | 护栏五红线 + 日志巡检 + 一键下线开关（环境变量） |
| API 费用失控 | 限流 + 月度用量告警 |
| Vercel 免费版函数超时 | 流式响应首字节快，超时风险低；持续观察 |
